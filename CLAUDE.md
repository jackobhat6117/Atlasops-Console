## Project

AtlasOps Incident Management Console: a senior React take-home (72-hour deadline). It is a responsive **web app** (not React Native) where ops engineers list, search, filter, sort, inspect, update and create service incidents. There is **no real backend**. The API is mocked in the browser with MSW and ships with the static deploy.

The authoritative spec is the assignment brief in `docs/` (`README.md`, `REQUIREMENTS.md`, `MOCK_API.md`, `SUBMISSION.md`). These files are **gitignored on purpose** (they're the company's text and are kept local only), so don't commit them or link to them from published files. Check `REQUIREMENTS.md` before building any feature. It has exact validation limits, required states and acceptance criteria.

The repo is currently a fresh Vite scaffold. The architecture below is the agreed plan. Treat it as the target, and update this file when reality diverges.

## Architecture (planned)

```
src/
  app/          providers (QueryClient, Router), app shell, MSW bootstrap
  features/incidents/  api.ts, schemas.ts (Zod), hooks/, components/, routes/
  features/users/
  components/   shared presentational UI
  lib/          http client + ApiError, URL-state helpers
  mocks/        MSW handlers + seeded in-memory DB (shared by browser and tests)
  test/         Vitest setup, render helpers
docs/API.md     our own mock API reference (committed; required deliverable)
```

### Key design rules

- **Mock API = MSW, also in production.** `src/mocks/handlers.ts` implements the contract in `docs/MOCK_API.md`. It must provide at least 1,000 incidents from a **seeded** generator, 200–1200ms latency, occasional random failures, `400 VALIDATION_ERROR` (with `fieldErrors`), `404 INCIDENT_NOT_FOUND`, `409 INCIDENT_VERSION_CONFLICT` (using `version` on status PATCH), and the dev-only `X-Mock-Failure` / `X-Mock-Delay` / `X-Mock-Conflict` headers. Tests use the same handlers through `msw/node`, with random failures disabled. If the service worker fails to register, show a friendly "API unavailable" screen, not a blank page.
- **One schema source.** Zod schemas in `features/incidents/schemas.ts` define the `Incident` model (REQUIREMENTS §3) and its types. They validate API responses at the trust boundary (`lib/http.ts`), the create form, and the request bodies in the mock handlers.
- **State ownership:** server state lives **only** in the TanStack Query cache. List search, filters, sort and page live **only** in the URL (`useSearchParams`), parsed and sanitized by one hook that drops invalid enum values and clamps the page. Form state lives in React Hook Form. Everything else is local `useState`. **No global store** (Redux/Zustand); the README must justify this choice.
- **Fetching:** query keys include the full list params. Pass the query `signal` to `fetch` (cancellation, so stale responses never overwrite newer ones). Use `placeholderData: keepPreviousData` for pagination and filtering. Search input is debounced before it reaches the URL. The HTTP client maps every failure (status codes, timeout, abort) to a typed `ApiError` and never shows raw errors or stack traces.
- **Mutations:** status change is the required optimistic mutation. In `onMutate`, snapshot and patch both the detail and list caches. In `onError`, roll back and announce via `aria-live`. In `onSettled`, invalidate. Handle 409 with a "changed by someone else, refresh" message. Assign and notes invalidate on success. A failed note must keep the user's text.
- **Navigation:** the detail route must return to the exact list URL (search, filters, sort, page). Carry the list's query string through to the detail link.
- **Accessibility is graded:** semantic `<table>` with `aria-sort`, keyboard-navigable rows, status and severity shown with text or icon (never color alone), Radix for dialogs and selects (focus trap, Esc closes, focus returns to the trigger), and form errors linked with `aria-describedby` with focus moved to the first invalid field. Notes are rendered as plain text. Never use `dangerouslySetInnerHTML`.
- **Required tests:** list rendering, search/filter, a successful mutation, a failed mutation with rollback, form validation, and one accessibility interaction (keyboard or dialog focus). Test observable behavior with RTL and user-event.

## Submission constraints

- The README must keep the 8 sections required by `docs/SUBMISSION.md` (Overview, Setup, Architecture, Decisions, Performance, Accessibility, Testing, Incomplete Work). Update it as features land, and keep "Incomplete Work" honest.
- Use small, readable commits. The reviewers reject a single giant commit. Commit only when the user asks.
- Don't use prebuilt admin templates. Every dependency must be justifiable, so avoid heavy packages for trivial features.
- The author will be interviewed on this code. Prefer simple, explainable code over clever abstractions.
